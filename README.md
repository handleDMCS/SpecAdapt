# SpecAdapt

Lightweight draft-side adaptation for speculative decoding. Windows PowerShell manages submissions; scripts and tests execute on Kaggle.

`src/specadapt/` is the standalone library (vocabulary bridge and decoder).
`src/demo/` contains the benchmarks, asset preparation and Kaggle CLI that use
the library. Only `specadapt` is included in the library wheel; Kaggle is a
development dependency. Demo commands below run from this repository's uv
environment, which makes `src/` importable. Configuration stays at the root.

## Gemini Notebook source

The [repository source page](https://handleDMCS.github.io/SpecAdapt/) contains
the code, tests, configuration, and design notes in one HTML document. GitHub
Actions rebuilds it on every push to `main`. A
[Markdown download](https://handleDMCS.github.io/SpecAdapt/specadapt.md) is also
available for file imports.

To enable publishing for a new copy of the repository, open **Settings > Pages**
and set **Build and deployment > Source** to **GitHub Actions**. Then run
**Actions > Publish notebook source > Run workflow** on `main`, or push a commit.
Wait for both the build and deploy jobs to finish. Pages publishes the included
source publicly.

To use it in [Gemini Notebook](https://notebook.google.com/):

1. Open or create your notebook and choose **Add sources > Website** (or **Web URL**).
2. Paste `https://handleDMCS.github.io/SpecAdapt/` and add the source.
3. Ask: "Using the SpecAdapt source, compare the vocabulary bridge design
   alternatives. Cite relevant file paths, explain tradeoffs, and suggest tests."
4. After code changes, re-import the URL and remove the old source. Check the
   commit printed in the imported text to confirm you have the intended version.

If the URL import fails, download `specadapt.md` from the page and upload it as a
file source. Google imports text from the supplied HTML page, without following
links to other files; the entire bundle is embedded directly for that reason.
See [Google's source import guide](https://support.google.com/gemininotebook/answer/16215270?hl=en).

`repomix.config.jsonc` controls the included files. It preserves complete code
and comments while removing blank lines. Credentials, local outputs, dependency
locks, and the generated seed cache are excluded; Repomix's secret check remains
enabled. The page shows its source commit and build time. This workflow prepares
context for a notebook; model selection is controlled separately in Gemini.

To preview the bundle locally with Node.js 22 or newer:

```powershell
npx.cmd --yes repomix@1.19.0 --config repomix.config.jsonc
node .github/scripts/render-notebook.mjs
```

The generated files are in the ignored `build/notebook-site/` directory.

## Pair 2 M1 demo

For repeated adapter development, see [draft-only oracle replay](notes/oracle-replay.md).
It reuses a recorded greedy target trajectory, loads only draft weights, and
reports acceptance and draft/bridge timings. Full demos below remain the source
of actual two-model throughput and numerical agreement checks.

Run these **sequentially** from the project root. Each runs its own target-only
reference and writes per-prompt results plus a summary into the downloaded JSON result.
Both use the same pinned Kaggle notebook environment.

```powershell
uv run --locked python -m demo.kaggle_run src/demo/prepare_data.py src/demo/demo_baseline.py
uv run --locked python -m demo.kaggle_run src/demo/prepare_data.py src/demo/demo_m1.py
```

The pair is Llama-68M -> Qwen2.5-7B-Instruct. Both use greedy decoding, fixed K=3,
one T4, a 4-bit NF4 target, and the 12 GSM8K test IDs in
[pair2_demo.toml](pair2_demo.toml). The baseline decodes draft text with its left
context and retokenizes into the target vocabulary. M1 adds an overlap map,
a contextual draft n-gram mapping trie (including subtoken merges), and longest
suffix continuation lookup in the current prompt, already verified output, and
a frozen cache generated by Qwen from 16 disjoint GSM8K **training** questions.
Cache proposals are always target-verified. Neither run reads reference answers.
M1 has no M2 training or M3 adaptive K. This is a small demo, not the full research
evaluation. Mapping-only proposals preserve the baseline's tokenization; the
acceptance gain comes from the continuation caches. This is a warm-cache M1
demo: its one-time target-generation cost is recorded separately from decoding.
The generated `m1_seed_cache.toml` can be bundled for subsequent runs; provenance
checks bind it to training IDs, model/data revisions and package versions. A
missing cache is rebuilt from training questions, never from test outputs.

Both local notebook metadata files pin the same Kaggle image digest and T4
machine shape. For a comparison that also eliminates differences between
notebook environments, use `src/demo/demo_compare.py` after `src/demo/prepare_data.py`: it loads
the models once, rotates execution order, and writes both result sets.

The result's `outputs` object contains `demo_results/{baseline,m1}.jsonl`, plus
metadata and summary objects. They include acceptance, accepted tokens per verification,
throughput, bridge overhead, and token-level agreement with target-only decoding.
After both finish, `uv run --locked python -m demo.compare_demo BASELINE.json M1.json` analyzes the two downloaded
submission JSON files and writes `results/pair2_comparison.json`, including a paired bootstrap
interval. Models and tests run exclusively on Kaggle.

## Setup

```powershell
Set-Location -LiteralPath "F:\SpecAdapt"
$env:PYTHONUTF8 = "1"

```

Keep your local Kaggle token in the ignored `.env` file. `kernel-metadata.json` supplies the notebook ID and compute settings.

## Run scripts in order

```powershell
uv run python -m demo.kaggle_run src/demo/check_cuda.py
uv run python -m demo.kaggle_run first.py second.py third.py
```

Paths are relative to the project root, including paths supplied with PowerShell backslashes. Quote paths containing spaces. The scripts share one Python session and namespace, like consecutive notebook cells. Each script's `if __name__ == "__main__"` block runs. A failure stops the remaining scripts.

Each submission produces one local file: `results\submission-<UTC-submission-timestamp>.json`.
The CLI saves the indented report directly there, including when resuming an
older submission. Reports with structured artifacts have `schema_version: 2`.
Top-level fields contain `timestamp`, `scripts`, `script_sha256`, `cache_owner`,
`status`, `error`, and `elapsed_seconds`. `run_log` holds captured stdout, stderr,
subprocess output, and tracebacks. `outputs` maps relative artifact paths to
structured JSON values for `.json` files and arrays of records for `.jsonl`
files. Other UTF-8 artifacts, including malformed JSON or JSON Lines, stay as
text. Files that are not valid UTF-8 use
`{"encoding": "base64", "data": "<b64>"}`. Explicit writes to `/kaggle/working`
use the `kaggle_working/` path prefix and are folded into the same JSON file.
The CLI verifies the submission timestamp, prints `run_log`, and exits nonzero
on failure. If Kaggle fails without producing the result, the CLI saves a JSON
report with `status: "platform_error"`, `kaggle_status`, available platform logs,
and an empty `outputs` object. Relative file access uses the bundled project root.
The input project bundle embedded in `submission.py` is unchanged.

Python source files and TOML configuration are bundled automatically. Credentials, virtual environments and previous results are excluded. Attach other input files as Kaggle datasets using `--dataset owner/slug`. Keep datasets and large model weights out of script output folders.

## Prepare persistent models and datasets

```powershell
uv run python -m demo.kaggle_run --cpu src/demo/prepare_data.py
```

This downloads pinned assets from [asset_plan.toml](asset_plan.toml) on Kaggle and publishes private Kaggle Datasets: one per model and one containing the five dataset sources for the four tasks. Nothing is downloaded onto your laptop except the result JSON.

The first run needs remote **KAGGLE_API_TOKEN** access to publish the caches. Kaggle CLI pushes do not carry Add-ons secret attachments, so either run initialization once from Kaggle's browser with the secrets enabled, or explicitly authorize a private credential input and attach it using `--dataset owner/specadapt-run-credentials`. The local `.env` is never bundled into code or results.

**HF_TOKEN** or **HUGGING_FACE_TOKEN** is needed only for the gated Llama 3.1 model and must have approved access to it. A missing token or a 401/403 response leaves that model pending while the other models and all datasets are prepared.

Run the same command again to check the cache. The CLI automatically attaches the matching private datasets. Preparation checks manifests and file sizes, logs model paths, and reads each Parquet file's row count. It does not contact Hugging Face on a complete cache hit.

To prepare and then use the paths in the same session:

```powershell
uv run python -m demo.kaggle_run src/demo/prepare_data.py your_experiment.py
```

Later scripts can use `MODEL_PATHS`, `DATASET_PATHS`, `DATASET_ROWS`, `PENDING_MODELS` and `CACHE_COMPLETE`. Dataset files are local Parquet files below each dataset path, retaining their config/split directories. The Code task has two sources: HumanEval and full MBPP. The script caches all source rows; it does not generate model outputs or select test/calibration subsets.

Changing an asset's pinned revision or file selection gives it a different cache name. A truncated cache fails validation rather than silently triggering a new download.

## Other commands

```powershell
# Validate and stage without contacting Kaggle or executing the supplied scripts.
uv run python -m demo.kaggle_run --dry-run --cpu src/demo/prepare_data.py

# Run the workflow checks on Kaggle CPU, with synthetic assets.
uv run python -m demo.kaggle_run --cpu --no-cache tests/run_tests.py

# Resume waiting/downloading after the laptop disconnects; use the printed timestamp.
uv run python -m demo.kaggle_run --resume SUBMISSION_TIMESTAMP
```

Use `--metadata relative/path.json` for another notebook, `--no-cache` to disable cache attachment, and `--poll-interval` / `--wait-timeout` to control waiting. A wait timeout does not cancel the remote job. Avoid concurrent submissions to the same notebook: Kaggle status/output APIs track the current run.
